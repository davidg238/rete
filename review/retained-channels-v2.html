Names, and what
answers to them

v1 asked “retained or event?”. That was the wrong frame, borrowed from the wrong system. A channel is a name. The only question that matters is what the name resolves to — and who is able to answer it.

your reframing

Channels are names, not pointers

You're right, and the code is unambiguous. resolve: builds a string path; a capability is a rooted prefix; attenuation is string extension. There is no object identity anywhere in the space.

(* kernel.ns — a capability is a name, and narrowing it is a string operation *)
resolve: rel = (
  outer checkPath: rel.
  ^ root , '/' , rel )                      (* a path. not a handle. *)

public channel: rel = ( ^ Channel new setRoot: (self resolve: rel) )

out: 'mode' value: v does not reference a thing. It names one. Which makes this a URL / filesystem problem, and means we can go read what people who solved naming problems already learned.

the question, precisely

Is the named thing a value, or a drainable queue?

a cell — it has a value

goal/mode · obs/health · goal/apps/<name>

Reading does not consume. Writing overwrites. Deleting is a distinct act. Asking twice gives the same answer.

a stream — it delivers occurrences

tel/print · sys/panic · goal/do/reboot

Reading consumes. Writing appends. Each element is delivered once. Asking twice gives you the next thing, or nothing.

The space today implements only the second. space_post / space_take / spaceRegister — every name in the namespace is a queue.

vocabulary

“Retained” is a kludge. Drop it.

The word is borrowed from MQTT, where a retained message is a broker-side delivery trick: the broker keeps the last message on a topic so late subscribers receive one. It names a delivery side-effect.

We do not want a delivery side-effect. We want to say this name has a value. That is a statement about what the thing is, not about how messages get handed out. Borrowing MQTT's word imports the suggestion that “retained” is a flag you could sprinkle onto an existing channel — and that is exactly the misreading to avoid.

Proposed vocabulary, used throughout this deck: a name resolves to a cell (it has a value) or a stream (it delivers occurrences). Everyone who has solved this before uses the first word or a synonym: a file, a znode, a key, a resource. Nobody calls it “retained”.

your objection — and you are right

Mixed namespaces are normal. I overstated this.

v1 argued: the two kinds don't share a verb set, therefore this is a deep problem. That was wrong, and your DNU objection is why.

A root capability with two children — one cell, one stream — is perfectly coherent. You reach either by name. Send the wrong message and you get an error. Why would you? You wouldn't. And systems do this everywhere without anyone calling it a flaw:

systemone namespace, several kindswrong verb →
Unixregular file · directory · FIFO · device · socketread() a directory → EISDIR
Plan 9every one of the above, plus synthetic serversan error string on the fid
ZooKeeperpersistent znode · ephemeral · sequentialKeeperException

So the difficulty is not the verbs. Scratch that argument entirely. The real question is one layer down.

the actual problem

Who is able to answer the name?

A capability is nothing but a rooted name, and it resolves through space.c. So a name that the space cannot answer is invisible to the capability system — there is no way to hand a job authority over something the namespace does not contain.

Put cells in a private Map inside the bridge job, and goal/mode is no longer a name in the space at all. It is a key in somebody's dictionary. It looks like a sibling of tel/print in every document we've written — same path syntax, same tree — but they now live in two different naming systems, and only one of them is reachable by a capability.

The question is not “C or nsl”. It is: can the namespace name a value — or do values live outside the namespace, where grants cannot see them?

prior art · naming

Plan 9: the namespace is the interface

Bell Labs, ~1992. Pike, Thompson, Presotto, Winterbottom, Ritchie. The claim is usually flattened to “everything is a file”, but the load-bearing version is sharper: every resource is a file server, exposing a namespace, spoken to with one small protocol.

prior art · the lesson

Don't add a kind. Add a server.

Plan 9 faced precisely our question — a namespace full of things that behave differently — and did not answer it by enumerating kinds in the kernel. It answered it by keeping the verbs uniform and letting whoever serves the name supply the semantics.

The proof is /net. In Plan 9 you open a TCP connection by writing to a file:

cat /net/tcp/clone          → "3"   a new connection directory
echo connect 10.0.0.1!80 > /net/tcp/3/ctl
... now read and write /net/tcp/3/data

No socket(). No new syscall. No new kind in the namespace. The network stack is a server that answers those names, and every existing tool — cat, shell redirection, the permission model — works on it unchanged, for free.

Applied to us: a cell need not be a new species of channel baked into space.c. It could be a prefix served by something. That is a genuinely different third option, and it is the one the literature points at.

prior art · our own ancestor

Linda already had the read we dropped

The tuple space this model descends from (Gelernter, Yale, ~1985) shipped four operations, not three:

Lindameaningwe have it?
output a tuple into the spaceyes out:value:
intake a tuple — destructiveyes take:
rdread a tuple — NON-destructiveno — never built
evalspawn a process to compute a tuple— (jobs cover this)

The non-destructive read was in the model from the beginning, and we shipped without it. That is a decent chunk of what we've been calling “retained”: not a new channel kind at all, but the missing half of the read verb.

It isn't the whole story — rd reads from a bag of tuples that still accumulates, whereas a cell overwrites. But it does mean the gap is smaller and better-precedented than “invent a second channel kind” makes it sound.

where the art stops working

We cannot mount porta. The node sleeps.

Plan 9's answer to remote is beautiful and, for us, unusable. You import a remote tree into your namespace and read it like a file — but that means every read is a round trip to a server that must be up right now.

duty cycle

The node wakes every ~15 s. A synchronous walk + read to the gateway on every access is not a thing it can do.

the radio

2–5% datagram loss, measured, on our own mesh. A read that can block or fail is now on the path of every config lookup.

partition

A node out of range must keep running on the last thing it was told. A mount gives it nothing.

Disconnected operation is a requirement, not a preference. And that single fact is what forces everything else: if you cannot fetch on demand, you must replicate — and the moment you replicate, you need to know what changed and what was deleted.

this is where seq, cursors and tombstones come from — they are not decoration

prior art · replication

So we are not building 9P. We are building etcd.

Once “replicate a named tree, tell me what changed since I last looked” is the problem, it is a solved problem, and it has a vocabulary. Our design has been reinventing it under other names.

etcd / ZooKeeperwhat it doesours (same thing)
revision / zxidmonotonic version stamped on every writeper-path seq
watch from revision Nreplay everything I missed, then streamchangedSince: cursor
tombstonea delete is an event, not an absencetombstone
compactionwhen may I forget old tombstones?our open question #6 — unanswered
leasestate that expires if its owner goes quiet— (we may want this)

Two things follow. First, steal the vocabulary — it's better than ours and it's what any future reader will already know. Second, steal the pitfalls: compaction-vs-cursor is a famous way to hurt yourself (a client whose cursor falls behind the compaction point can never catch up and must resync from scratch). We have that exact bug latent, and it is currently written down as a shrug.

prior art · the cautionary tale

LOCUS: transparency you pay for later

UCLA, early 1980s (Popek & Walker). A distributed Unix that went all the way: a replicated filesystem, and processes that could fork onto another machine — the whole network as one machine image. It worked, it was genuinely impressive, and almost nothing since has copied it.

The reason is the law we already wrote into the protocol:

Location transparency must not become failure transparency.
Waldo, Wyant, Wollrath & Kendall — A Note on Distributed Computing (1994). The four irreducible differences: latency, memory access, partial failure, concurrency.

Hide the network well enough and callers stop writing code that copes with it — so the failure doesn't go away, it just surfaces somewhere with no handler. Plan 9 got away with far more transparency than LOCUS partly because its interface was file I/O, which everyone already knows can fail. A `read()` returning an error is unremarkable. A remote `fork()` failing is a catastrophe with nowhere to go.

That is the standard our design has to meet, and it is why take: never crosses the wire: a destructive remote read is a consensus problem wearing a local read's clothes.

the piece you asked about

What the bridge actually is

The bridge is not privileged code, and it is not a protocol handler. It is an ordinary supervised job that happens to have been handed the radio capability plus grants over the sync prefixes. If it crashes, the supervisor restarts it and porta sees a late check-in — nothing worse.

why a bridge at all

Four jobs, one object

1 · it holds the radio

So that no other job has to. A sensor job publishes to obs/health and is done. It never learns that anything left the building.

2 · it is the replication engine

Pull goal/** since cursor, apply locally. Push changed obs/** + queued events. Persist the cursor. That loop is the protocol.

3 · it is the one door

Auth, size caps, overflow policy, version skew — enforced in exactly one place, because there is exactly one place. Not by discipline; by construction.

4 · it is fault-isolated

An ordinary job means an ordinary crash. Let-it-crash applies to the network stack like anything else. The node keeps running on its last known goal.

And note what this buys against LOCUS: the node is the initiator. Porta is passive. That is deep-sleep-correct, NAT-friendly, and it means a partition looks like “a check-in that hasn't happened yet”, which is a state every part of the system already understands.

now the fork — sharpened

Can a cell be built in nsl? Yes — and that's the trap

The bridge can absolutely hold a Map of path → value. Where it breaks is the second reader. The space has post and take; it has no request/reply. So a job cannot ask another job for a value and get an answer — there is no call. Which leaves three ways to let the supervisor read goal/apps/**:

routewhat it really costs
hand the supervisor a reference to the bridgethe supervisor now knows the bridge exists. The grant stops being the whole story — authority arrives by object reference, not by name. This is the thing the capability model exists to prevent.
every job keeps its own copy, rebuilt by replaying whenever:works — until a job restarts and has missed the events. So it must ask for a refresh; so you add a refresh channel; so you add re-publish rules, and racing, and “who has seen what”… you are hand-rolling cache coherence, per consumer.
put the cell in the namespaceevery job reads it through the capability it already holds. Nothing new is learned by anyone. Cost: C.

Row two is the disease this protocol was written to cure. Special rules that multiply per feature — that is the exact indictment of porta v1 in §1. Rebuilding it inside the node, one consumer at a time, would be a bleak way to lose the argument.

the three options, stated

A, B and C — what each one is

A · the cell becomes a second kind in the space

space.c gains a value slot, a per-path seq and a tombstone flag. A name is created as a cell or a stream, and answers the verbs that make sense for it. Jobs reach cells through the capability they already hold — nothing new is granted, nothing new is learned.

goal peek:  'mode'              → Mode { … }   non-destructive
goal put:   'mode' value: m     overwrites, bumps seq
goal clear: 'apps/blink'        → tombstone
goal whenever: 'mode' do: [ … ] fires ON CHANGE, not per element

new prims: spacePeek / spacePut / spaceClear / spaceChangedSince

B · the space learns to route a prefix to a server

space.c gains one thing — a dispatch hook: this prefix is answered by that object. No cell logic in C at all; a cell becomes an ordinary nsl class that serves goal/**. Drivers could serve dev/**. This is Plan 9's move.

space serve: 'goal' with: Cells new     Cells is ordinary nsl
space serve: 'dev/env0' with: bme280

a job still just writes:  goal peek: 'mode'
— the space routes the name to whoever serves it

new prim: spaceServe:with:   (+ re-entrancy, GC rooting, reactor)

C · nsl only — no VM change (what §3.1 literally promises)

The bridge holds a private Map of path → value/seq/tombstone. Nothing else in the system can see it. Any other reader must go through one of the two bad routes on the previous slide.

Where I land, and what I'd want to know first

A, and not C. Option C is cheap exactly until the second reader shows up, and the design has already promised there will be one (the supervisor, reacting to goal/apps/** “as it reacts to any channel”). Paying in hand-rolled cache coherence to avoid ~200 lines of C would be trading the good argument for the cheap one.

B is the better idea and probably not yet. It is what Plan 9 would do, it is genuinely more powerful, and it has a real second customer waiting. But drivers do not require it — a driver works fine as a job reacting on streams — so today it has one true customer, and “a general mechanism with one customer” is how kernels get fat. I'd rather build A, and revisit B when the second customer is real. If B ever lands, A's cell becomes its first server and nothing is wasted.

Two things I'd settle before writing any C:
1 · #21 is now load-bearing. A cell must distinguish holds nil / holds nothing / tombstoned. Today the seam cannot even tell the first two apart at take:. Fix that with the cell, not before it.
2 · Steal etcd's vocabulary and its scars — revision, watch-from, compaction. Specifically: decide what happens when a node's cursor falls behind the point where porta forgot its tombstones. Right now the answer is a shrug, and it is a real way to strand a node forever.
