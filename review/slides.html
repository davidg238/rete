nsl-tuvm · 2026-07

Script Zephyr.
Don't replace it.

A ~24 KB capability-secure OO scripting layer for 256 KB-class devices — nRF52840 + OpenThread — with supervised jobs, immutable messages, and remote provisioning over the LAN.

The gap

Toit got the model right — but struggles with Zephyr

What Toit proved:

  • An ergonomic OO language on the device
  • Supervised, crash-isolated jobs
  • Immutable messages between them
  • Push code over the network (jag) — no reflash cycle
  • Performance and type safety are achievable on-device

Two bets that leave our target class open:

  • Sized for ESP32-scale RAM — a tight fit for the 256 KB nRF52840 class, where Thread radios, coin cells, and years-long deployments live
  • Does not leverage Zephyr's catalog of maintained drivers — every sensor starts from scratch, in-language
The wedge

Each side has what the other lacks

Zephyr has: hundreds of maintained drivers behind uniform APIs, devicetree, OpenThread, power management, every Cortex-M part.

Zephyr lacks: a safe, ergonomic, remotely-serviceable programming model. C application code needs a flash cycle per change.

Put a tiny OO layer on top of Zephyr.

Reuse a Zephyr display driver — don't write one.

The language is the coordinator; C is the datapath.

The language lineage

Toit → Smalltalk → Newspeak → nsl — each hop, priced

Toitthe operational model to beat: jobs, messages, push-code its static types + runtime are sized for ESP32-class parts — and a typed language done well is a compiler-team-sized project. This is a one-engineer effort with a 256 KB part: both budgets say spend on operability, not typing — abandoned knowingly, not dismissed
Smalltalkthe smallest ergonomic dynamic core: keyword messages, everything-an-object ambient authority — any object reaches any global; no way to confine a driver; reflection everywhere by default
Newspeaktakes late binding to its conclusion: every name is a message send — class names, even the superclass, resolve through the enclosing module. No globals falls out; so do first-class modules (hence pushable code), capabilities as constructor arguments, and mirrors — reflection as an object you grant, not an API every object carries full semantics (NLR, activation reification) ballooned a tiny VM — proven the hard way (ns-oevm)

The substrate · Piumarta & Warth, VPRI 2008

OEOM — the kernel that survived the graveyard

A complete object system from three structures and one operation:

  • object — word 0 names a vtable
  • vtable — itself an object: selector→method bindings + a delegate for lookup fallback
  • send — look up through the delegate chain, then apply

Classes, inheritance, metaclasses — all built inside the system from those parts. Smalltalk's metaclass tower, boiled to its minimum.

Why it matters here

Everything is a send — so there is one choke point

Every feature that must apply to all behavior was implemented once, at lookup — not per type, not per call site.

  • Encapsulation — the access check runs on every send (the method cache never caches a verdict)
  • Let-it-crash — DNU and faults funnel into one crash-record path the supervisor consumes
  • Capability confinement — one enforcement surface; the reason confinement is cheap at 24 KB
  • Debugger & mirrors — reflection is just more sends, granted as a capability

The alternative at this scale (Berry's shape: tagged unions + C switch) re-implements each of these per type, per path. When confinement is the product, the uniformity is load-bearing.

The deliberate theft

We kept the minimalism, froze the openness

What it costs on a 256 KB part:

  • Per object: one RAM word — which the precise GC needed anyway (it doubles as the layout descriptor)
  • Per class: one const vtable in flash — XIP, never marked, never copied, zero RAM; ~200 in the image, a thousand instances share each
  • ~14 builtin vtables ≈ one per physical layout the GC must distinguish — already the floor

Piumarta's "open" — mutate the model at runtime — is the part we deleted:

  • Vtables solidified to const XIP structures; dispatch semantics pinned
  • On a node that runs unattended for years, "the object model cannot change under you" is a feature
  • The design's real strength: it stayed powerful after its headline feature was removed — shrank to a few flash structs + one C function, still carries the metaclass tower, capabilities, and the debugger

The enabling cuts

Two deletions buy the whole simplification

✕ Non-local return
^ in an escaping closure is a compile error. Collection combinators (detect:ifNone:, anySatisfy:, inject:into:) are the sanctioned early exit — most “break” is really a search.
✕ Fibers
Jobs are run-to-completion event handlers, not threads. Multi-step protocols become explicit state machines — a stdlib idiom, not a VM feature.
✓ What the deletions buy
The reify-on-escape / unwind / cross-fiber / growable-stack cascade is deleted, not deferred. One heap-side language stack in one known state — which makes the crash boundary, watchdog safe-points, and precise GC rooting simple enough to trust at 24 KB.
✓ It matches the host OS
Zephyr workqueues, ISR bottom halves, and OpenThread callbacks are all run-to-completion. The scripting layer composes with Zephyr's grain instead of scheduling against it.
The strongest argument

No fibers is the deep-sleep-correct model

A suspended fiber's stack cannot survive power-down.
Reactor state in explicit objects and channels rehydrates naturally — wake-from-sleep is just another event.

  • Always-on and deep-sleep nodes run the same programming model
  • State that must persist across sleep is exactly the state the design already makes explicit
  • Battery-class Thread nodes are the target — this is a requirement, not a nicety
Messages

Immutable values, shared by reference — zero copy

  • Closed algebra (Toit's proven design): null · bool · int · float · string · bytes · symbol · list · map · record — recursively closed, depth-bounded, acyclic by construction
  • A mutable object is unrepresentable as a message — that structural fact is what makes crash isolation safe
  • On the single shared heap, inter-job messages pass by reference: zero copy — a simplification the shared heap makes safe (per-process heaps, as in Toit, must copy)
  • Only the boundary serializes (network / flash / drivers) — CBOR-compatible wire encoding, so CoAP tooling debugs porta traffic for free
Confinement & robustness

Channels are capabilities · handlers may crash

Capability = a channel namespace rooted at a path prefix.

  • Attenuate by extending the prefix: sensors/ → sensors/temp/
  • A job can only speak where it has been granted — no ambient authority
  • Drivers surface as granted capabilities, not globals

Let it crash — supervision in nsl, not C.

  • A faulting handler unwinds to the reactor; the node keeps running
  • Supervisor logs, restarts, quarantines on repeated failure
  • Soft watchdog (safe-point budget) + hard Zephyr WDT as the backstop
The model, named

Actors at the grain, tuple space at the joints

A job is an actor in everything but addressing:

  • private state · one message at a time, to completion
  • contained crashes · supervisor restart policy
  • gen_server minus the PID

Multi-step behavior = an explicit FSM (lib/fsm.ns):

  • the actor's behavior function; state in ordinary objects
  • the same explicitness that makes deep sleep rehydrate — wake is just another event

The rendezvous is Linda's, verbs and all:

  • out: — publish into the space
  • take: — destructive read
  • whenever: — standing reaction

Why paths beat PIDs on a fleet:

  • restart transparency — the path outlives crash, restart, even a code push; producers never notice (Erlang grew registries for this)
  • attenuation by prefix — the address is the security model
  • the substrate agrees — Zephyr's own IPC idiom (zbus) is channel pub-sub

Within a job: Newspeak — synchronous sends among objects. Between jobs: immutable values through the space. Two semantics, each at the boundary where it belongs — the same line BEAM draws.

The constraint

256 KB is the design target — RAM, not flash, decides

nRF52840 RAM budget — 256 KB total
Illustrative working budget; banked and ratchet-tested from Milestone A (addendum A2)

Runtimes designed for larger parts don't fit what remains after Zephyr + OpenThread — this class needs a deliberately small engine. The tuvm budget (~24 KB) leaves ~96 KB of language heap for the image, tuple space, and messages — with headroom banked, and any RAM regression a test failure.
