nsl-tuvm · performance · 2026-07

Optimize the right thing.

Microbenchmarks say one thing. A real workload on real hardware says another. And the axes that actually decide whether a product ships — build time, observability, deployability, failure legibility — are mostly unbenchmarked by anyone.

Companion to “Script Zephyr. Don't replace it.” That deck makes the architecture argument. This one answers the question it provokes and does not settle.

What we're building

A product that measures and controls values in the physical world

  • Sensors and actuators, wired to real things — a thermal array, a valve, a doorbell, a display
  • Battery or mains, deployed in the field, expected to run for years
  • A fleet — you do not get to visit it, and you do not get to reflash it by hand
  • Built by a small team who must also ship the product the device is part of

Every performance question below is downstream of this. A number that does not change whether this ships is a number worth reporting honestly and then not optimizing.

The obstacle course

What stops you shipping one

Chips
choose one, source it, bring it up, live with it for a decade
Drivers
every sensor, every bus, every part — written and then maintained
Software
the application logic, written safely enough to run unattended
Deployment
getting the first version out, and the fiftieth
Maintenance
diagnosing and fixing a fault in a device you cannot reach
Only one of these is a language problem
and it is not the one benchmarks measure
Bridge from deck 1

Zephyr removes one roadblock outright

  • The widest choice of parts of any embedded OS — every Cortex-M, RISC-V, Xtensa class we care about
  • Hundreds of maintained drivers behind uniform APIs, described by devicetree
  • OpenThread, power management, networking, filesystems — already there, already tested

Reuse a Zephyr display driver.
Don't write one.

That is deck 1's whole argument: put a tiny OO layer on top of Zephyr rather than replacing it. The language is the coordinator; C is the datapath.

What's left

Software is the roadblock that remains

What is the fastest, safest way to write, deploy and maintain the application that sits on top?

That question has a performance component. It is not the whole question, and it is not usually the deciding one — but it is the one everybody asks first, so this deck answers it first.

The two questions

Is it fast enough? — and fast enough for an agent?

Question 1 — is it fast enough?
Almost everyone asks this, and almost everyone answers it with a microbenchmark. Acts I–III answer it with a device instead, and say plainly where we are slow.
Question 2 — fast enough for an agent?
Almost nobody asks this. An agent's scarcest resource is not MIPS, it is context — and slow loops, flaky tests and silent failures are what burn it. Acts IV–V answer this one.

The deck closes where it opens: these two questions, answered as far as the evidence goes, with the gaps named rather than papered over.

Act II · the trade, stated first

What 256 KB costs — and what it buys

The constraint that produced our column:

  • nRF52840-class parts — 256 KB of RAM — were a key deliverable, not a stretch goal. Thread radios, coin cells, years-long deployments live there.
  • After Zephyr and OpenThread, what remains for a language runtime is tens of KB. We bought RAM with speed.

The constraint that produced theirs:

  • Toit is sized for ESP32-class RAM and is faster for it. Same problem space, different constraint, different optimum — and Toit is the reason there is a target worth aiming at.
  • uLisp and CircuitPython are different bets again, and each wins rows below.

Rule for every comparator row in this deck: state the constraint that produced it. A number without its constraint is an insult; with it, it is an engineering result. Where a comparator wins, we say so plainly and without hedging.

Act II · why

Because OrderedCollection is written in nsl, not in C

  • Every do: is a real block activation. Every at: is a real send with a real bounds check. There is no fast path, because there is no special case — the uniformity that makes capabilities and the debugger cheap costs exactly here.
  • Putting the collection classes in C would buy the row back and cost flash and surface. That is a footprint decision, not a quality gap.
The same trade, in the other direction
Toit's library is larger because Toit is self-contained. Ours is small because Zephyr's C carries the drivers. That is an architecture difference, not a virtue — and it is the same sentence read from the other end.

The mechanism, precisely. Publishing a 64-element frame walks it twice: once to copy it into an immutable List, then again to validate it, where checkValue: and depthOf: each independently recompute the same element rank — two prim calls and roughly thirteen sends per element to re-derive what was known one line earlier. Named because it is fixable, not because it is fatal: filed as #78, estimated at ~20% off publish, and it will be A/B'd on the device against the very spans that found it rather than argued.

Act III · suppose it did matter

A method is a field in a vtable — so optimization is a field write

The object model (Piumarta & Warth's OEOM) is three structures and one operation:

  • object — word 0 names a vtable
  • vtable — selector → binding, plus a delegate for lookup fallback
  • send — walk the delegate chain, then apply

Every call in the system is a send. There is exactly one choke point.

What that buys, concretely
A binding holds a closure. Swap the closure for a hand-written C function and the method is now native — with callers, the interpreter, and the .oimg image format all unchanged. No JIT. No recompile of the callers. No format break.

This is not a plan. It is a one-field write that has been done and measured, on the same board, in the same binary.

Act III · measured, same board, same binary

Hanoi 20: →

What this number is, stated so it cannot be misread. This is the fully-inlined AOT ceiling — the recursion collapses to raw C, allocation-free, no GC. A real bytecode→native compiler preserving send and GC semantics would land between the interpreter and this bound. The claim is the lever, not the number.

A claim this deck explicitly refuses to make: “0.103 s against Toit's 3.0 s — 29× faster than Toit.” That compares native C Hanoi against Toit's compiled Hanoi: a C-vs-Toit number wearing an nsl-vs-Toit label. The honest and still-strong claim is that a substituted method runs at C speed — at which point it has stopped being a language comparison at all.

Act III · the strategy this makes available

Write it in nsl · measure on the device · drop C in where the measurement points

  • Ship the interpreter. Small, uniform, confined, debuggable.
  • Profile the real workload — Act I's spans, on the device, in the field, not a benchmark you hope resembles it.
  • Substitute surgically. One binding at a time, each with a before/after on hardware.
Why this ordering is the point
Optimizing before measuring is how you end up 40× faster at something that was 3% of the path. The mechanism is only valuable because the measurement exists to aim it — Act I is what makes Act III more than a party trick.

And the cost of being wrong is one field. There is no rewrite to regret, and no compiled artifact to keep in sync.

Act IV · observability

Do you know what your code is doing — with nothing attached?

  • Latency spans — named, nested, min/max/mean/p50/p95, kept on the device
  • Heap and GC — live bytes, high-water, collection counts
  • Channel overrun counters — cumulative, never reset, first occurrence announced once
  • ISR and mailbox counters — coalesced ticks, shed posts, drops
Served by the node itself
A web page from the device, or a CBOR record over the mesh into a store. No JTAG, no host, no debug build, no “can you reproduce it on the bench”. Total cost of the span facility: of DRAM on a part with spare.

This is the difference between a system you can reason about and one you can only guess at. The next slide is what it caught.

Act IV · the proof

A 23 ms job reported as

  • The seam offered one span_now(), documented as free-running microseconds
  • The Zephyr backend converted cycles → µs before returning, so its value domain wrapped at , not 2³²
  • A u32 difference is only valid in the units the subtraction happens in
  • Completely silent on the host, where the backend unit really is the microsecond — only the device could catch it
How it was caught
A phantom sample in the ≥1 s bucket on a web page served by the node. The arithmetic then pinned it exactly — an ordinary 23 ms job. Fixed by moving the subtraction into the backend and renaming the stamp so nobody reads microseconds into it again.

Instrumentation that is only good enough to confirm what you already believe is decoration. This one contradicted us, which is the only evidence that it works.

Act IV · failure legibility

What it tells you when it breaks — and the time it told us nothing

What the design provides:

  • Supervised jobs — a faulting handler unwinds to the reactor and the node keeps running
  • Structured crash records on sys/crash — tag, text, channel — not stack-trace prose
  • Counted sheds and drops, rather than a k_oops and a reboot

And the counterexample, which is the more useful half:

#65 — the node left the network in silence
back-to-back requests took it off the network entirely. No panic. Nothing on the console. Recovered only by a hardware reset. Our own instrumentation said nothing, because nothing counted the thing that ran out.

Root-caused and fixed 2026-07-22. Idle connections pinned every RX packet buffer, and with no keep-alive there was no timer of any kind to reap them — so freeing RX required receiving. Widening the slab alone dropped client-side timeouts from to over a comparable run. The fix is real; the indictment stands — it was invisible for a day, which is exactly what the next act says must never happen.

Act V · the premise, not the conclusion

We are not building another scripting language

We are building a pipeline an agent is comfortable in.

  • The operator of a fleet increasingly is an agent, running the same loop a developer runs: observe → hypothesize → change → verify → bank evidence
  • A platform is “agent-first” exactly to the degree every stage of that loop is machine-legible and fast. Not “has an API”
  • This act does not introduce new evidence. It re-reads Acts I–IV — which is the whole argument: these properties were not built for agents, and they are what an agent needs
Act V · the scarce resource

An agent's scarcest resource is context

Whole system, language + VM: the stdlib plus the hand-written C substrate ≈ . An agent can hold the entire system in one context window — semantics, implementation, and seam.

The demonstration, not the claim. One session, one agent, one context, no handoff: edited span.c, kernel.nsl, the node's application, an upstream Zephyr driver, four test files and five documents — and produced the Act I table.

Indicative, not a benchmark. Two systems only, chars ÷ 4 as a token proxy, and “surface” is not yet defined rigorously across peers. Filed as #66: the full peer set with a published methodology — what counts as surface, each system's source of truth, and how uLisp's C builtin table and CircuitPython's C-modules-plus-bundle are handled. Until then this card is a sketch, and it says so.

Act V · determinism as a budget

A test that cannot flake is a context budget

  • Time is virtual in host tests — advanceMillis: makes timing deterministic by construction
  • A test therefore cannot flake on timing, so an agent never burns a single token distinguishing flake from fault
  • Inline (* expect: *) oracles are machine-checkable; the single-test cycle is seconds
Why this is a performance slide
A flaky test does not cost you a re-run. It costs an agent the context it spends deciding whether the failure was real — and that context is the budget that decides whether the loop closes at all.

Stated honestly: static types would help an agent too — machine-checked interfaces, cheap early feedback. We did not buy them, for reasons deck 1 records. What actually burns agent context is slow loops, flaky tests, silent failures and unobservable state, and this system spends its budget there instead: a tiny closed surface, fail-fast conventions, and schemas at the wire and prim seam with dynamism inside.

Act V · the design law

Never-silent instrumentation — and this act claims Act IV for it

If it can happen, something machine-readable must say it happened.

  • A dropped event, a swept reaction, a shed post, a restarted job — each gets a counter or a record. Cumulative, never reset, first occurrence announced once
  • A human can sense that something is off. An agent only sees what is surfaced. For a human operator this is good practice; for an agent operator it is the difference between a diagnosable system and an invisible one
  • So the spans in Act IV were never a metrics feature. The 99.6% accounting is “we know what our code is doing”, and the wrap defect is the proof it works. #65 is the proof of what happens where the law was not yet applied

This is the slide that makes Act IV retroactively an agent argument rather than an engineering-hygiene one. It does not repeat those slides — it claims them.

Act V · the underrated argument

Capabilities are an agent sandbox the platform enforces

  • A capability is a channel namespace rooted at a path prefix, attenuated by extending it
  • Grant an agent a rooted cap over fleet/lab/** and its confinement is structural — enforced at the one send choke point, not by a prompt and not by a policy document
  • The enforcement predates the agent question entirely. It is there because drivers should not be globals
Few platforms can say this
“The agent cannot touch production” is a sentence most systems can only implement as a convention. Here it is the same mechanism that stops one job reading another's channel — already tested, already load-bearing.
Act V · what is not built

Gates, not aspirations

Before an agent may push autonomously:

  • Signing (G5) — who may push code. No autonomous push before it
  • Canary + auto-rollback (G1) — bounded blast radius as a platform primitive, not agent etiquette
  • Letter-log replay — capture a node's inbound letters, replay under the virtual clock, turn a field fault into a seconds-long host test
  • Remote eval — hypothesis-testing on a live node without a deploy

Before this deck's own numbers are complete:

  • #66 — surface in tokens, full peer set, published methodology
  • #67 — time-to-deployed-change vs a flash cycle
  • #68 — build time and peak RSS, recorded rather than remembered
  • #69 — a checker asserting every figure in this deck still matches its witness

Four badges in this deck are open issues, and the deck was built to produce them rather than to hide them. If the numbers do not materialise, the argument is wrong and should say so.

Where we came in

Two questions, answered as far as the evidence goes

Is it fast enough?
For this class of workload on this hardware — yes, and more usefully, we can say where the time goes and where we are slow, by name. The worst microbenchmark row is real, is in the shipping job, and decides nothing. If it ever does, the fix is one field in a vtable.
Fast enough for an agent?
The loop is seconds and machine-legible: deterministic tests, structured crash records, on-device spans, a system small enough to hold at once, and a sandbox the platform enforces. Two of the four numbers that would settle it are not measured — and they are filed, badged and visible on the slides above.
