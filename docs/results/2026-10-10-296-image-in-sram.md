## The question

#403 showed the RP2350's 16 KB XIP cache costs 2.1–2.7× on the interpreter's *code*. #296 asks the
other half: is the *data* side — the 168–189 KB `.oimg` blob executed in place from QSPI flash, every
bytecode word, constant, vtable and binding read through the same cache — the rest of the floor between
8.51 µs/activation on the board and ~0.1 µs on a desktop? And the question behind it (David, 2026-10-10):
with 520 KB on this part, what does a RAM-resident image buy, and where does nsl stand against
MicroPython once placement is out of the way?

## 1. Assumptions made without David (each is reversible)

1. **One binary per arm pair, the arm chosen at boot on the console**, not two builds — #403's own finding
   is that a layout shift alone moves this board 2×, so a cross-binary off/on comparison would measure
   placement. The window is 8 s after the 3 s USB settle; the default arm when nobody answers is `flash`.
2. **The blob copy is a static 192 KB buffer** (`OEVM_BLOB_SRAM_CAP`), not a heap allocation: the arena is
   the only other large RAM object and both must be sized at link time. RAM used: 431,628 B of 520 KB with
   the 128 KB arena, the 192 KB copy buffer and the hot path in `.ramfunc`.
3. **Both boards take the `rpi_pico2/rp2350a/m33` image**, as the 2026-10-10 record did; the WeAct's own
   board definition (#403) is not used here, so the numbers compare with yesterday's row directly.
4. **Arm 2 (`OEVM_SPIKE_296_HOT2`) is a second binary**, because it changes code placement, and it is
   compared only with itself across the blob arms. It puts the three functions the host profile shows once
   per send beside the `OEVM_HOT` set (§4).
5. **MicroPython is the comparator, not CircuitPython**: upstream v1.29.0's `RPI_PICO2` build (fetched
   2026-10-10 from micropython.org), stock, no frozen modules of ours. The scripts are the nsl workloads
   re-expressed in the shape each row naturally takes in Python, with both shapes given where the two
   languages disagree on what a row is (§3).
6. **The workloads are #296's three** (Hanoi 18, blockcost at 1/10, richards ×3) in one node,
   `Spike296Node.nsl`, so one boot answers all rows for one arm.
7. The firmware spike lives behind `OEVM_SPIKE_296=1`; no standard image changes. The branch is not for
   merging as-is: what survives is whatever §6 earns.

## 3. The host column — nsl, MicroPython, CPython, one machine

ms, opti7040, self-timed. nsl is the host image VM at `-O2`; mpy is the MicroPython unix port; cpy is
CPython 3. Workload scale is the board node's (1M inline / 100k outer).

| row | what it measures | nsl | mpy | cpy | nsl/mpy |
|---|---|---:|---:|---:|---:|
| hanoi 18 (262,143 method activations) | a method send + frame | 26–30 (first run 44) | 33–40 | 13–15 | **0.8×** |
| baseLoop (1M) | an inlined counted loop + add | 39 | 34 | 39 | 1.1× |
| blockValue (1M) | one block/closure call per iteration | 85 | 88 | 54 | 1.0× |
| methodSend (1M) | one monomorphic send per iteration | 87 | 121 | 58 | 0.7× |
| blockCapture (1M) | a closure writing a captured variable | 139 | 113 | 62 | 1.2× |
| closureMake (1M) | a fresh closure per iteration | 106 | 64 | 75 | 1.7× |
| ocDo (100k × 10 elements) | `oc do: [:e \| e]` vs `for e in oc: e` | 160 | 21 | 11 | **7.6×** |
| ocDoCall | the nsl shape in Python: `for e in oc: f(e)` | 160 | 79 | 29 | 2.0× |
| ocAt (100k × 10) | indexed read in a hand loop | 139 | 40 | 20 | 3.5× |
| richards (1 iteration, verified) | the OS-simulation benchmark, sends + allocation | 108 | 206 | 50 | **0.5×** |

**Reading it.** With placement out of the picture, nsl is at parity with MicroPython on sends and blocks
and ahead on richards. The rows it loses are the collection rows: `do:` costs a real block activation per
element where Python's `for` is a bytecode, and `at:` goes through `OrderedCollection>>at:` →
`Array>>at:` → a primitive where Python's `oc[j]` is one bytecode. That is #37's finding, on the host,
with a MicroPython column: the interpreter's send path is not the gap; the collection protocol's depth is.

Counted, not inferred (coverage build, 100k × 10-element probes on the host):

| per element | frames pushed | `send_resolve` | what it is |
|---|---:|---:|---|
| `oc do: [:e \| e]` | 1.0 (+1 per `do:`) | 0 (+1 per `do:`) | one block activation per element, through `OP_BLOCK_INVOKE`, no send |
| `oc at: j` | 1.0 | 1.0 | one send and one frame; `Array>>at:` underneath is a primitive, no frame |
| `self bump: j` | 1.0 | 1.0 | the same shape as `at:` |

So `do:` costs exactly what a method activation costs, per element, and Python's `for` costs a bytecode.
Nothing about placement or RAM changes that; what would is a cheaper block frame (`push_frame` copies
five registers and sets up `home_ctx` per activation today) or a lighter activation for a non-capturing
block. That is #37's lever, priced here.

## 4. One activation on the host — what touches the blob

Counts from the coverage run, per method activation (17,891,626 of them):

| per activation | count | where |
|---|---:|---|
| `oimg_resolve` (tagged word → oop) | **3.0** | 2.5 from `OP_LD_CONST` (`cm_const_at`), 1 from the selector load in `OP_SEND` |
| of which `OIMG_TAG_BUILTIN` (bounds check + `builtin_registry[i]` load) | 3.0 | the constants Hanoi loads are builtins; the switch and the registry indirection are the cost |
| `is_in_blob` range checks | ≥ 6 | every `cm_const_at`, `closure_entry`, `obj_vtable` on a blob object |
| `lookup_method_cached` | 1 | the global method cache, hit every time here; **not** in the `OEVM_HOT` set |
| `check_access_allowed` | 1 | returns on the first compare (`ACCESS_PUBLIC` always, ledger row 25); **not** hot |
| `oevm_int_demote` | 2.5 | on every `OP_LD_CONST`; **not** hot |
| `push_frame` register copies | 5 | `ncopy` loop |

Two things fall out before any board number:

- **Relocation is 3 resolves and ~6 range checks per activation.** A loader that rewrites the blob's
  tagged words into oops once (possible only when the blob is in RAM) deletes all of them from the hot
  path; `cm_const_at` becomes `m->constants[i]`. On the host that is of the order of 10–15 % of an
  activation (~350 cycles); on an in-order M33 reading the words through XIP it is the hypothesis #296
  states. Arm 1 measures the XIP part of it; relocation itself is the next spike, not this one.
- **Three functions run once per send from flash on the RP2350 today.** `OEVM_HOT` covers
  `run_interpreter`, `send_resolve`, `push_frame`, `is_truthy`; `lookup_method_cached`,
  `check_access_allowed` and `oevm_int_demote` are called from them and live in flash. Arm 2 moves them.
  The access check is the ledger's row 25: a call per send that can never refuse. Deleting it is the
  simpler fix; arm 2 prices keeping it.

## 5. The spike firmware

`zephyr/src/main.c` under `OEVM_SPIKE_296`: a boot-time console window (`sram` | `flash` | `bootsel` |
`reboot`), the copy into `spike296_blob_sram`, `oimg_load_blob` on the copy, and after `main:` returns a
parked console that answers `bootsel`/`reboot` — the bootrom's `rom_reset_usb_boot` and `rom_reboot`, so
a board on opti7040's USB can be re-armed and reflashed from here with no hand on it. `Spike296Node.nsl`
is the workload. `OEVM_SPIKE_296_HOT2=1` is arm 2. Build (msi-7d43, inside `~/zephyr-esp32/.venv`):

```

  bash run.sh --board rpi_pico2 --node Spike296Node.nsl --conf-extra prj_rpi_pico2_usb.conf \
  --build-dir build-rpi_pico2-296
```

Link report, arm 1: FLASH 369,284 B, RAM 423,436 B of 520 KB, hot path at `0x20000104`.

**Found on the way, worth its own line (2026-10-10 18:45–19:00).** The first spike image boot-looped on
the WeAct: banner, the arm prompt, then a reset ~8.4 s after boot, no fault text, USB device numbers
climbing. Cause: `wdt_rpi_pico` starts the hardware watchdog at driver init (`CONFIG_WDT_DISABLE_AT_BOOT`
is unset in every RP2350 build here; `WDT_RPI_PICO_INITIAL_TIMEOUT` defaults to 8,388,607 µs), and
`observer_start()` is what takes it over — every proven image reaches it ~3.1 s after boot. An 8 s
console window in front of the observer was a reset at 8.39 s, every boot. The fix is the window after
`observer_start()`. Two lessons that go to `ZEPHYR_LESSONS.md` if the spike lands: on the RP2350 the
watchdog is running from before `main()`; and a watchdog reset writes no retained note, so a loop with
no fault text and no note is the watchdog, not the firmware's own crash boundary. The spike image now
also carries a boot guard (four boots without reaching the node → BOOTSEL) so a looping image can be
replaced without a hand on the board.

**Why the board rows are blank.** Both RP2350s run the 2026-10-10 images, which have no path back to the
UF2 loader; the first flash of this image needs BOOTSEL held by hand. From then on `spike296_console.py
... --then bootsel` + `flash_uf2.sh` is the whole cycle, and MicroPython's `machine.bootloader()` gives
the same for the Zero.

**Verdict on #296: refuted on the RP2350, cleanly.** With the interpreter's hot path already in SRAM
(#403), moving the whole 189 KB image from XIP flash to SRAM changes nothing on the send, block and

cache. The bar was richards −20 %. The flash→SRAM→flash sequence on one binary reproduces to the
millisecond, so this is not noise and not placement. The data side of the XIP cache is not where the
per-activation floor lives; the instruction count is (§4). This is the fourth negative result in the
E5→E8 series and it closes the question #296 asked.

the ledger's rows 30, 31 and W3 (interning, patch as install, inline caches), and its cost is 189 KB of
SRAM that the nRF52840 does not have. The case for it has to be made on those, not on µs/activation.

## 7. What this says for the 512 KB question — the guidance

1. **Placement is finished as a lever.** #403 took the instruction side (2.1–2.7×); this spike shows the
   data side is worth 0–5 % and the last flash callees 1 %. Everything per activation is in SRAM. There
   is nothing left to move. The RP2350 row on the STIC table should read "hot path in SRAM, blob in
   flash" and stay there; `OEVM_RAM_HOT` is the whole placement story.
2. **The floor is instructions, ~1,250 cycles per activation, and the host says where they are** (§4):
   three tagged-word resolves and ~six blob range checks (relocation on load, needs the image in RAM:
   the one reason left to put it there), five register copies and a `home_ctx` set-up in `push_frame`,
   a method-cache hash and compare per send, a vestigial access check per send (ledger row 25; delete
   it), `oevm_int_demote` on every constant load (canonicalise at image-build time instead). None is a
   10× item; together they are the 20–30 % that separates 8.4 µs from the ~6 µs an in-order M33 at 150
   MHz should give this design. The 10× item does not exist without a JIT, and #395 already placed that
   in flash, not RAM.
3. **nsl is already faster than MicroPython per call on this silicon** (0.60–0.73× on sends and blocks,
   level on richards) and 4–7× slower on collection iteration and indexed access, where `do:` costs a
   frame per element (§3, counted). A 512 KB nsl that is "comparable to MicroPython" is therefore not
   a VM project; it is #37: a cheaper block activation, or `do:`/`at:` over the kernel's own
   collections lowered by the compiler the way `to:do:` already is (ledger row 19). That is where the
   next spike goes, and it needs no RAM.
4. **What the 512 KB buys the language, then, is not speed but the ledger's deferred rows**: a writable
   image in RAM (189 KB of the 450 KB ceiling, impossible on the nRF52840) gives runtime interning (row
   30), patch as a real install (row 31), per-site inline caches (W3) and through them the one deferred
   feature family, virtual classes and mixins (rows 1, 2, 6). The decision to take that is a design
   decision about the language, to be made on those grounds. The measured speed cost of leaving the
   image in flash is 0–5 %.
5. **Found on the way, to land regardless:** the RP2350 boot watchdog (§5) in `ZEPHYR_LESSONS.md`; the
   `spike296` BOOTSEL/reboot console words as a standard RP2 facility (a board on a remote USB port
   can be reflashed with no hand on it — it cost tonight an hour and two of David's button presses);
   the `-pg` artefact in §2.

## 9. Follow-on, same evening: where the 1,250 cycles go, and the compiler's share

David's question after §7: can `do:`/`at:` be AOT'd, or must they be lowered? The answer needed a cost
model, so the image was decoded (`patch_hanoi.py`'s reader) and the rows re-read against it.

**The bytecode the compiler emits.** `hanoiMove:from:to:temp:` is 27 instructions, 16 executed per
activation on average (8 on a leaf, 24 inside). `baseLoop`'s loop is 10 instructions per iteration;
`OrderedCollection>>do:` is 10 per element plus the block's own; `OrderedCollection>>at:` is 11 on
the in-bounds path plus the send. Roughly 40 % of each is register traffic no semantics requires:
a compare that first copies its operand into a fresh window, a copy of every send's result into a
temporary nobody reads, `^ n` copied to a temporary before `OP_RET`, the constant 1 loaded three
times in one method, `nil` materialised for an `ifTrue:` whose value is dropped.

**The cycle model, from the board rows (WeAct, arm 1, blob in flash).**

| | per | cycles at 150 MHz |
|---|---|---:|
| one bytecode (baseLoop: 10 per iteration, 2.74 µs) | bytecode | **~41** |
| a send round trip beyond its bytecodes (methodSend − its ~17 bytecodes) | send | **~430** |
| a block round trip beyond its bytecodes (blockValue − its ~15) | block invoke | **~390** |
| a Hanoi activation = 16 bytecodes + 1 send | activation | 656 + 430 ≈ 1,090 (measured 1,270) |

The host executes the same bytecode at ~15 cycles each. On the M33 the 41 is fetch, four-field decode,
the jump table and an opcode body that bounds-checks every register index against `num_registers` on
every `LD_REG`/`LD_CONST` (the debug hooks are already compiled out of the board image,
`OEVM_NO_DEBUG_HOOKS=1`, so they are not in this number).

**So, the answer to the AOT-or-lower question, priced.** `do:` cannot be AOT'd to any effect: its
per-element cost is one block round trip (~390) plus ~12 bytecodes (~490), and native code can remove
only the latter's loop share while the block invoke stays (the flat loop forbids re-entering the
interpreter from C, ledger row 19). Lowering a literal block into the caller removes the round trip
and most of the bytecodes: ~900 → ~300 cycles per element, the MicroPython number. `at:` can be
AOT'd: it saves the callee's ~11 bytecodes (~450) and keeps the send (~430): 12.3 → ~9 µs. Lowering
it removes the send too: → ~4 µs. Both lowerings need the receiver's class at the call site, which
the compiler does not have; that is the same gap as #395's. The native `at:` spike was not run
tonight because the model already bounds it; the number it would add is "a send that lands on a
native closure", worth having when leaf AOT is next.

**The lever that needs no receiver class: emit fewer bytecodes.** The copy-propagation ceiling was
measured by hand-writing the Hanoi method's bytecode the way a peephole pass would — 17 instructions,
11 executed per activation against 16 — into the image (`patch_hanoi.py`), host and board, same VM,
same everything else:

| hanoi 18 | compiler's bytecode | hand copy-propagated | ratio |
|---|---:|---:|---:|
| host, ms (noisy, best of 3) | 29–32 | 21–28 | ~0.8 |
| WeAct, ms per run (µs/activation) | 2217 (8.46) | **1801 (6.87)** | **0.81** |

Every other row of that boot is identical to arm 1 to the millisecond (baseLoop 2742, blockValue 6688,
methodSend 7542, richards 9133/9132/9252), so the build is otherwise the same binary and the 416 ms is
the five bytecodes: 1.59 µs per activation, **~48 cycles per bytecode removed**, which is the model's
41 within its error. Hand-written copy propagation on one method is worth 19 % on the send-heaviest
workload the suite has; a pass that also hoists constants and picks RET's register would take Hanoi to
about 10 executed bytecodes and ~25 %. (`logs/weact-peep-flash.log`.)

**Guidance, revised from §7 item 2:** the order is (1) the compiler's register allocation and
peephole — no VM change, no receiver class, every row gains, 20–30 % on sends from the Hanoi ceiling
alone; (2) the interpreter's per-bytecode overhead — drop the per-opcode bounds checks the compiler
already guarantees, and keep `pc`/`ctx` out of memory, worth another fraction of the 41; (3) then the
send path (relocation, row 25, `oevm_int_demote`), each a few percent; (4) guarded lowering of
`do:`/`at:` once there is a receiver-class story, which is the only thing that reaches MicroPython's
collection rows. AOT of leaves is real but smaller than any of these.

## 10. Same night, later: the peephole built, and what it uncovered in the allocator

**The pass.** `ns_compile_oevm.py` now ends every frame with a peephole (`NSL_PEEPHOLE=1|A|B|0`):
copy-propagation of `LD_REG t, x` into its one consumer when nothing intervenes, and dead-store
deletion of `LD_REG`/`LD_CONST` whose register is rewritten before any read, with liveness as a
walk of the frame's control flow. It leaves alone `self`, the Context register and every register a
nested block reaches by index through `home_ctx` (the compiler records those), and treats any opcode it
has no operand model for as a barrier. Over the spike image: 18,299 → 15,251 instructions (−16.7 %),
the blob 188,896 → 176,952 B; Hanoi 27 → 20 instructions. The nsl suite with it on: 293 passed, 0 failed, 14 skipped; the
aux line had one real red, `debugger-integration`, whose `dbg:out` check pinned "just past the
`countTo:` send" as pc 6 — the pass had moved the send to 5. The gate now derives that index from the
image (`test_debugger_integration.py`), and passes. The other aux marks on opti7040 (`*-py`, `cmake-parse`)
are this machine lacking pytest and cmake; the combined run (peephole + §10's allocator change) was
started on both opti7040 and msi-7d43 at 22:05 and its result is to be read before anything merges:
`/tmp/suite-combined-msi.log` on msi-7d43.

**First board run: the send rows gained, the allocating rows lost.** Hanoi −13 %, methodSend −5 %, ocAt
−9 %, but blockValue +60 %, closureMake +22 %, ocDo +12 %. Three experiments took that apart:

**The mechanism.** The sweep bins each interior dead run by size class, so the one big coalesced run
lands in the catch-all bin, and the trailing run goes to the bump pointer. Any live object near
`heap_top` after a sweep makes the trailing run small; from then on every allocation that misses its
exact bin and the bump tail walks the ~57 empty bins between its size class and the catch-all, splits
the big block, bins the remainder, and the next allocation walks again. The peephole only changed
which object survived a collection and where; the fragility was the allocator's, and any program can
trip it.

**The fix** (`gc.c`, two parts): the largest interior run from a sweep is kept out of the bins as
`big_free` and carved O(1) like a second bump region; and a 64-bit mask of non-empty bins makes the
remaining cross-bin search a count-trailing-zeros instead of a walk. Measured on the WeAct, arm-2
placement, blob in flash, both compiler modes:
