# Line-in over the console cable — spike for rete#311

**Question (David, 2026-10-02):** the Toit and st-oevm generations mixed console and commands on one serial link
with SLIP. Is that needed again to get to one USB cable, on all boards?

**Answer: no.** Plain text lines sent down the console cable reach the VM on all three board families, while the
console keeps printing on the same cable. No framing was needed. What the boards did need is two different receive
paths, and the C6 one was found by hanging the board.

## What was built

- `platform_debug_readline` on Zephyr (`nodus/oevm/src/backend/zephyr/platform_zephyr.c`) — it was a stub answering
  "no line". It is the seam the desktop debugger already reads its `dbg:*` lines through (primitive `PRIM_pf_readLine`).
- `nodus/oevm/zephyr/ReadLineProbe.nsl` — prints `rl:ready`, then echoes each line as `rl:got <n> <line>`.
- `nodus/oevm/zephyr/prj_linein_spike.conf` — the one Kconfig line the C6 path needs.

## Result per board

| board | console | receive path | lines echoed | longest line | cost |
|---|---|---|---|---|---|
| RP2350-Zero | USB-CDC, the only cable | polled, armed once | 6 of 6 | 200 chars whole | not measured |
| `nrf4ec0` (dongle) | USB-CDC, the only cable | polled, armed once | 5 of 5 | 200 chars whole | static RAM unchanged (257948 B); flash not isolated from the probe's own size |
| `c6spare` | CP2102N UART bridge | **interrupt-driven**, 256-byte queue | 27 of 27 | 400 chars whole; 20 lines back to back, 20 of 20 | not measured |

All sends were made through a second handle on the port while the console collector kept reading it (RP2350: one
handle, no collector).

## Two findings

1. **A USB-CDC console takes no input from a pure poller.** The class driver starts its first OUT transfer only from
   `irq_rx_enable` (or from a `poll_in` that already got a byte), so the desktop's write times out
   (`SerialTimeoutException: Write timeout`, `nrf4ec0`, 13:52). One `uart_irq_rx_enable` call fixes it; `poll_in`
   then works. Same code in both Zephyr trees (`usbd_cdc_acm.c`).
2. **A polled reader hangs the C6.** Once about `CONFIG_UART_ESP32_RX_FIFO_THRESH` (22) bytes queue in the UART
   FIFO the whole system stops, and the hardware watchdog resets it ~22 s later
   (`rst:0x7 (TG0_WDT_HPSYS)`, three times: 13:58:46, 13:59:34, 14:00:17). Lines up to 24 chars always worked; a
   50- or 200-char line always hung it; a 30-char line did both. The same 200-char lines sent in 8-byte chunks 20 ms
   apart went through 5 of 5 — so it is the queue depth, not the length. **The cause is not established**: the
   build has no UART interrupt handler, and what stops the system was not traced. The interrupt-driven path does not
   show it (400 chars, and 680 bytes back to back).

| `c6spare` (polled image) | 57 s (14:01:33 → 14:02:30) | no `rst:` line |
| `c6spare` (interrupt-driven image) | 36 s (14:04:08 → 14:04:44) | no `rst:` line; the counter continued (27 → 28) |

and that is the case the observer judges. This is still open on rete#311.

## The C6 on one cable (the CP2102N)

Run at 14:10 with the USB-JTAG cable still plugged in but unused: `ESPTOOL_PORT` and `CONSOLE_PORT` both set to the
CP2102N.

| step | through the CP2102N | result |
|---|---|---|
| flash | esptool, no button press | `Wrote 377236 bytes … Hash of data verified.` |
| reset | RTS pulse | `rst:0x1 (POWERON)`, then `build-id porta-v1-final-1289-g0ba0ee4-20261002T141014` — the image just built |
| console | collector | `rl:ready` |
| line in | second handle | `rl:got 1 one cable`, then a 200-char line whole |

One hand-step: the console collector was stopped for the flash and restarted after it, because esptool and the
collector otherwise split the ROM handshake (rete#154). `run.sh` does not do that itself; the board harness does.
**Repeated at 14:15 with the USB-JTAG cable pulled** (David): flash verified, `build-id …-g811dbad-20261002T141541`,
`rl:got 1 jtag pulled`, a 200-char line whole — but only with `ESPTOOL_PORT` naming the CP2102N. Left to pick the
port itself, `run.sh` aimed esptool at `/dev/ttyACM0`, which was the nRF dongle, and failed with exit 2 (rete#316).

**Repeated at 14:18 through the USB extender** (two hubs deep, `1-1.4.4`, instead of a motherboard port): flash
verified at the same speed (860 kbit/s), `build-id …-gd42a848-20261002T141803`, a 400-char line whole, 20 of 20 burst
lines.

## Part 2 — the debugger on the C6 (same day, 15:50–16:10 MST)

**Question (David, the follow-up on rete#311):** the per-bytecode hooks, the enable flag, and a held program that
has timers. **Answer:** set a breakpoint, stop, step, inspect, continue — all on `c6bench` over its one cable from
the gateway; the board was held 21 s at the breakpoint against an 8 s liveness deadline and was not rebooted;
the debug build costs 11.6% per bytecode and 494 B of flash.

### What was built

- **The enable follows the build** (`platform_debug_enabled`, `platform_backend.h`). A board has no environment
  to carry `OEVM_DEBUG`, so the hooks image (`OEVM_DEBUG_HOOKS=1`) is the debug image: the Supervisor prints
  `dbg:ready` at boot and waits for the cable; the production image, hooks compiled out, never enters the loop.
  One switch, not two. Both image paths read it (`oimg_loader.c`, the solidifier's emitted entry); posix still
  reads `OEVM_DEBUG`, and the `debugger-integration` gate passes on both paths unchanged.
- **A held VM is not a wedged VM** (`observer_core.h` §3.2, `held`). The Zephyr read sets `debug_held` around
  its block; the observer samples it and re-latches the feed age while it is set, so the clock restarts from the
  RELEASE. §3.1 (a repeating timer whose ISR stopped) is deliberately not held off. Property 10 in
  `tests/test_observer_core.c`: held 80 s past an 8 s appCad, no trip; released and still stuck, fires 8 s after
  the release. (Before the change the same timeline trips at 9 s: the property fails to compile without the
  field, and fails at the first held sample with it absent from the rule.)
- `zephyr/DebugProbeC6.nsl` — a 1 s timer, `appLiveness: 8000`, each tick calls `countTo:` (the host gate's shape).
- `zephyr/tools/dbg_session.py` — ONE handle on the cable; `session` runs the whole flow and prints a verdict,
  `run` just sends the boot-time `dbg:continue` and streams.

### The session (run 2, the clean one; run 1 was identical except the driver counted the boot it had asked for as a reset)

Built from the working tree that became `bcfa3d6` (the build ids read `g780b6dc-dirty`: a rebased tip dropped before the push in favour of a merge, so that hash is on no branch), flashed from the gateway through the CP2102N
with the collector stopped (`Hash of data verified`), driven by `dbg_session.py session --reset --hold 20 --watch 60`:

| step | sent | answered | when |
|---|---|---|---|
| boot | RTS pulse | `rst:0x1 (POWERON)` … `dbg:ready` | 15:55:29.0 |
| list | `dbg:methods` | 21 lines `<id> <selector> <tag>`, `countTo:` is id 3, `dbg:ok methods` | |
| arm | `dbg:break 3 0` | `dbg:ok break` | |
| run | `dbg:continue` | `dbg-probe: ticking`, then `dbg:paused break 3 0` | 15:55:31.0 |
| **hold** | nothing for 20 s | **nothing** — no `rst:`, no `WEDGE`, no tick | 15:55:31.0 → 15:55:51.1 |
| inspect | `dbg:inspect` | `dbg:stack off=0 r0=an Object r1=1 r2=nil …` (`r1` is `n`, tick 1) | 15:55:51.1 |
| step | `dbg:step` | `dbg:paused step 3 1` | |
| over | `dbg:over` | `dbg:paused step 3 2` | |
| out | `dbg:out` | `dbg:paused step 2 7` (back in `tick`) | |
| disarm | `dbg:clear 3 0` | `dbg:ok clear` | |

12 of 12 steps, 62 ticks in the 60 s watched, no reset line anywhere after the boot. The deadline the observer
was judging is 8000 ms (the declaration); the hold was 2.6× it. On the pre-change rule this is the exact shape
`wedge-detect` reboots at 9 s.

**The production image of the same probe** (`g780b6dc-dirty-20261002T155119`, no hooks): no `dbg:ready`; `ticking`
0.2 s after the build-id line, tick 10 at +10 s. The one switch holds on both sides.

### What this does not cover

- `dbg:pause` does not exist: a running program cannot be stopped from the cable; breakpoints are set at boot
  (`initialLoop`) or while paused. The boot-time wait has no timeout, deliberately — a debug image is on a cable by
  definition; what would earn a timeout is wanting a hooks image to run unattended, which nothing does today.
- `CONFIG_UART_INTERRUPT_DRIVEN` is still a spike overlay (`prj_linein_spike.conf`), not in `prj_esp32c6.conf`:
  folding it in changes every C6 image including the bell's, which this session did not flash.
- Breakpoints are still `<methodId> <offset>`; no front end from a file and line. The `.stmap` beside the image is
  the other half.
- **Coincident, not proven:** `c6bench` logged `rst:0x1 (POWERON)` at 15:49:16, minutes after a pyserial open on
  its CP2102N with DTR and RTS deasserted, while the collector held the port. Opening a second handle may reset a
  C6 through the devkit's auto-reset pair; the session driver pulses RTS on purpose, so it did not care.

## What part 1 did not cover

- The C6's other USB port (the chip's own USB-JTAG) as the single cable: the console is not on it.
- One receive path for all boards. The interrupt-driven path should also work on USB-CDC (the class driver
  implements that API) and would replace the polled one; it was not run on the dongle or the RP2350.
- Binary traffic. If the gateway protocol is ever carried over the cable, that is the case that needs framing.
