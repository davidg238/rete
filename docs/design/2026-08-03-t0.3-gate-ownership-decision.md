# T0.3 gate ownership: one script measures, one script decides

**Date:** 2026-08-03
**Status:** decided and landed (`fdab28e`, `9f6cd44`, branch `fix/143-t0.3-one-verdict`)
**Issue:** #143 · **Refs:** #110, #31, #63, #145

## The decision

`nodus/tuvm/tools/footprint.sh` **measures and banks**. It renders no verdict.

`review/tests/t0-gates/ratchet.sh` **is T0.3** and renders the only verdict, at the
tolerance the spec states: **+2%** on host text, MCU text, and MCU data+bss.

`run_tests_oevm.py::run_footprint_gate()` runs `ratchet.sh`.

## Why

Two gates covered the footprint and they did not share a tolerance. `footprint.sh`
ratcheted internally on **any** growth (`-gt baseline`); `ratchet.sh` allowed +2%. On
2026-08-03 `mcu data+bss = 69048` **failed one and passed the other** — the same number,
two verdicts.

`review/test-suites-spec.md` §T0.3 settles which is right. It states the gate FAILS if
text or RAM grows "beyond baseline + 2%". That is `ratchet.sh`'s number, and `ratchet.sh`
already named itself T0.3 in its header, already treated `footprint.sh` as
measurement-only, and already carried the #110 hardening (integer-guarded operands, the
`(TOTALS)` row addressed by name rather than by position).

Two implementations of a verdict is one more mechanism than the job needs. The spec's
number was kept and the duplicate decider was removed, rather than teaching both scripts
the same 2%.

## The finding that made this urgent

**`ratchet.sh` had no caller.** Nothing in the repository invoked it — not the suite, not
any script, not CI. The spec-conformant T0.3 gate had never run. What *did* run was the
suite calling `footprint.sh`, which enforced a tolerance the spec never asked for, on
three of the four figures, and reported SKIP without the cross toolchain.

Repointing the suite at `ratchet.sh` therefore also **widens** coverage: host text is
ratcheted for the first time, where the old wiring checked only the two MCU figures.

## What this does not decide

- **`handles.o` is in the MCU measurement set and absent from the host one** — the two
  configs measure different object sets. Filed as #145.
- **A missing MCU baseline file makes `ratchet.sh` print a note and exit 0**, dropping the
  RAM ratchet from a passing run. Also #145.
- **§T0.3's prose still names `footprint.sh` as the comparer.** Its +2% number is what was
  implemented; its script name is now wrong. `review/` is David's review-agent tree and was
  deliberately not edited here — the correction is his call.

## Verification

The gate was falsified, not observed passing. MCU text banked at 33000 → FAIL; at
**33812 → PASS**; at **33811 → FAIL** — the +2% boundary is exact to the byte. Host text
banked low → FAIL. Toolchain absent → exit 77 → a yellow SKIP naming the MCU half as the
part that did not run. `run_footprint_gate()` returns PASS/SKIP/FAIL on all three paths.
Full suite: 239 passed / 0 failed / 14 skipped, every aux gate green. `fdab28e` alone is
green under both the old zero-tolerance verdict and the new +2% one, so the pair is
bisect-safe.

The baselines re-banked alongside this (#143 item 2) carry their own rationale in
`fdab28e`'s commit message: +1668 B text was measurement scope, +2898 B was real growth,
attributed per landed change-set with no residue.
