# Node identity is the factory link address

**Decision record — 2026-09-11.** Closes the question #118 asked and #242 reopened.
Decided by David, over the phone, on the facts below. **Not yet built**: it is a wire
change that wants a rebuild of every node, so it lands as its own rung. Until it lands,
`platform nodeId` still answers the build-time define `OEVM_NODE_ID` (`platform.c:1508`)
and two boards flashed from one image still share a name.

Supersedes #186's choice of a build-time id. #186 was right on the evidence it had; the
two grounds it decided under (the id must be human-readable; any other value needs a
mapping table) were removed by the gatekeeper design's role layer
(`porta/docs/design/2026-08-22-gatekeeper-first-cut-design.md` §5.2), which is what #242
argued.

## The decision

1. **The device id is the factory link address of the board**, read from silicon at boot
   and formatted the same way on every board port. `platform nodeId` (prim 155) answers
   it. The build-time define `OEVM_NODE_ID` is **deleted**, not defaulted — a node that
   cannot read its factory address does not boot with a made-up one.
2. **The human name is the role, not the id.** `goal/name`, porta-authored and
   node-echoed at `obs/name`, is where `bathroom-1` lives. Nobody reads the device id.
3. **The build-time board name moves to `obs/build`** as a field, so the mapping
   board-name → device is asserted by the node on every boot rather than curated in a
   table (#170's failure shape does not apply to derived data).
4. **The id is a LAN id.** It need only be unique within one porta's space. There is no
   WAN id, and none is invented here: if one is ever needed it is the gateway's id
   prefixed onto the node's, never a third value minted on the node.

## Why the factory address, and why it is one mechanism for both radio families

A Thread node carries three addresses and only one is a hardware id:

| address | source | survives full erase | who sees it |
|---|---|---|---|
| **factory EUI-64 / base MAC** | nRF: Nordic OUI + FICR die id (`ieee802154_nrf5.c:116`, UICR override optional); C6: eFuse base MAC (`ieee802154_esp32.c:518`) | yes | commissioner at join; the sticker |
| OpenThread extended address | random, U/L bit set, regenerated by a full-erase reflash | no | child/neighbour tables — the bench labels `7adf` `4ec0` `92c2` are this |
| mesh-local EID, RLOC16 | routing | no | the mesh |

`review/tests/CLAIMS.md` already records that the extended address is *current identity,
not a serial*, and cannot be correlated with the sticker without a wire read. The factory
address can.

On the C6 the one eFuse base MAC is what WiFi, BLE and 802.15.4 all derive their
addresses from, by fixed offsets. On the nRF the die id plays the same role. So a WiFi node
and a Thread node answer the same question from the same kind of register: **one primitive,
one format, no per-radio identity scheme.**

**Duplicates become impossible rather than detected.** Factory addresses are allocated
from registered blocks, not drawn at random, so the collision question is not probabilistic.
(Even the random extended address, at 1000 nodes over 64 bits, collides at roughly
3 × 10⁻¹⁴.) Runtime detection via the boot-counter fingerprint (#242) still ships, as the
check that the impossible did not happen.

## The one choice inside the decision: which nRF register

The nRF52840 has two factory values in two registers, both die-unique, both erase-proof:

- **FICR `DEVICEID`** — what the 802.15.4 driver builds the EUI-64 from.
- **FICR `DEVICEADDR`** — the BLE static address, which is what is printed on the sticker.

**Chosen: the sticker value, on both families.** Then the id porta shows is the id written
on the board, and correlating a node in `porta get` with a board in a hand needs no wire
read. On the C6 that is already the eFuse base MAC (the sticker prints the WiFi MAC). On
the nRF it means reading `DEVICEADDR`, not `DEVICEID`.

## What lands when this is built

- `platform nodeId` reads the factory address on every board port (C6 family, nRF52840 DK
  and dongle, MagTag/S2, WROOM-32; host answers a fixed test value or the interface MAC —
  decide at build time, and say which in the record that closes it).
- One formatting rule, written once, tested against a golden per family.
- `OEVM_NODE_ID` removed from `zephyr/run.sh`, `CMakeLists.txt`, the build assertions
  added by `151643f`, the collector env files and `docs/tutorials/02-board.md`.
- `obs/build` gains the board name → **`protocol/MANIFEST.cddl` edit**, which moves the
  manifest SHA-256 (the `obs/build` pin and `check_provision.py`'s served-hash side).
  **Sequence it with #285**, the other pending manifest edit, and with a gateway deploy.
- Every node is reflashed. The old spaces (`c6bench`, `c6spare`, `nrf4ec0`, …) become
  historical from that date, the same way the 2026-08-22 spaces did (#186); analysis that
  crosses the date reads both.
- Close-out promotes this to `porta/docs/ARCHITECTURE.md` (identity section) and
  `protocol/PROTOCOL-NSL.md` (the node-id field's definition), per the promotion rule.

## What this does NOT decide

- Authentication. A node id is a name, not a credential; #288 (the mesh runs on stock
  sample credentials) is a separate question and this record does not touch it.
- Any WAN or cross-gateway scheme. See item 4.

Refs #118 #242 #186 #170 #285 #288.

## Addendum — 2026-10-02: the tree re-measured, and the four points the record left open

Re-measured at `d0d6d7b` before building (#253 burn list, item 2). The decision above stands
unchanged. What follows resolves what it left open and corrects what went stale. Resolved by
Claude under the design posture in `CLAUDE.md`; each is one line to overturn.

**Stale in the record above.**

- The primitive is the `PRIM_pf_nodeId` case in `nodus/oevm/src/platform.c`; the line number
  cited above has drifted.
- **#285 is closed** (2026-09-18, `9b6332a`). The `obs/build` field is now the only pending
  manifest edit, so there is nothing to sequence it with except the gateway deploy.
- The removal list is short. `OEVM_NODE_ID` also lives in `zephyr/cmake/gen_node_id.cmake`
  (the generator, with a tailscale → hostname → `unnamed` fallback chain), in the host half
  of `platform.c` (`oevm_host_node_id`), in the host gates (`tests/host_ota/run.sh`,
  `tests/porta_sync_host.sh`), in `docs/tutorials/03-porta.md`,
  `nodus/oevm/zephyr/docs/BOARD_PORTS.md`, `porta/docs/GETTING-STARTED.md`, and in comments
  in three node sources.
- The collector env files carry no id. They live outside the tree (`$BENCH_CONFIG_DIR`), and
  the board name is the **file name**, resolved by `bench::board_for_port`. That lookup is
  kept: it is the source of the board name `obs/build` now carries.
- Two board ports postdate the record: `rpi_pico2` (RP2350) and `feather_rp2040`.

**1. Format: lowercase hex of the address bytes, most significant first, no separators.**
Twelve characters for a 48-bit address. No colons, because the id is a path segment and a
CLI argument. The golden per family is captured from a board and compared with its sticker
by hand, once; on the nRF that comparison is also the check that `DEVICEADDR` in this byte
order is what the sticker prints.
*(Hand-check done 2026-10-02 on `nrf4ec0`, sticker `D2:66:6D:1A:F9:19`: the byte order is
right. David, same day: the top two bits of the first byte are forced to 1, because the
sticker prints the address that way and raw `DEVICEADDR` need not have them set. Record:
`docs/results/2026-10-02-118-node-id-board-proof.md`.)*

**2. How it is read.** Zephyr's `hwinfo_get_device_id` answers the eFuse base MAC on every
ESP32 family, so those ports share one read. On the nRF it answers `DEVICEID`, which is the
register this record chose against, so the nRF port reads FICR `DEVICEADDR` itself. That is
two reads behind one function, and the formatting is written once above them.

**3. A board with no radio answers its flash serial.** *(Revised the same day, David: "RP
boards have no id ... really".)* The RP2350 and RP2040 ports have no radio, so no link
address. Their factory-unique value is the flash chip's serial, which Zephyr's
`hwinfo_get_device_id` answers there: 8 bytes, so 16 hex characters under point 1's rule. It
is factory-set and survives erase and reflash, so it is not a made-up id, and it puts the RP
ports on the same read as the ESP ports, leaving the nRF as the one exception. There is no
sticker, but the USB stack prints the same bytes as the board's serial string, and
`obs/build`'s `board` field carries the bench name. The first draft of this point had the
primitive fail on RP boards, on the ground that no RP node asked for an id; that
under-weighted the RP2350 being cabot's motion board (#301, #302), where a bridging node is
planned. An id therefore has two legal lengths, 12 and 16, which #305 inherits.

**4. The host answers what it is given, and nothing when given nothing.** The record offered
a fixed test value or the interface MAC. Both are refuted by the fleet gates: `host_ota` runs
several VMs on one machine, and either choice gives them one id. So the host's stand-in for
silicon stays the environment variable, and the made-up `<hostname>-NNNN` fallback is deleted
with the rest: unset means the primitive fails, the same as a board that cannot read its
address. `nodus/tests/23_mprof/05_node_id.nsl` asserts the deleted shape and is rewritten.

**The board name.** It keeps today's build plumbing under a new name, loses the fallback
chain, and is published as an optional `board` text field on `obs/build`. A build that was
not told a board name publishes none. By the encoded-bytes key order the field sits between
`chip` and `build`.

**Not in this rung.**

- The ingest gate on the id's length and charset (porta#18's v2 form) is **#305**. With the
  shape fixed by point 1 it becomes one rule, decided after this lands.
- `OtaBridgeNode.nsl.tmpl` writes `Build` by hand with a synthetic version, which the
  `host_ota` gate depends on. It gains no `board` field and is left as it is.

**Closed 2026-10-02.** Built, proven per family and deployed the same day: the gateway serves the
manifest with `board` in it and every bench node was reflashed onto its factory id. The decision
now lives in `porta/docs/ARCHITECTURE.md` §3.8 and `protocol/PROTOCOL-NSL.md` §5.3 (the `id`) and
§8; the evidence is `docs/results/2026-10-02-118-node-id-board-proof.md`. This record stays as the
why.
